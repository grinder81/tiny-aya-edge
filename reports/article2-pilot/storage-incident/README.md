# C8 storage interruption and recovery gate

The C8 run stopped during degrade-one exports, before any comparative native KL or proxy measurement. The last successful status observation reported eight passed exports and about 360 seconds of completed native budget. Those are last-observed values, pending recovery and inspection of the original ledger; no export result is reconstructed from them.

C: had only 10,911,744 bytes free when investigated. The Ubuntu disk reported read/write I/O errors, an aborted ext4 journal and a read-only remount; export and resource-sampler processes ended with bus errors. Ubuntu then failed to start. Host free space subsequently rose to about 35 GB without this agent deleting files. The cause of that increase is unconfirmed. The [kernel excerpt](kernel-excerpt.log) and [observations](observations.json) preserve the diagnostic evidence. A backup through `wsl --export --vhd` failed with a sharing violation; no completed backup is claimed.

The resource checks covered the WSL virtual disk and C8 artifact cap but omitted the actual backing Windows volume. That implementation gap allowed host exhaustion despite apparent Linux free space. Microsoft documents that WSL's displayed virtual capacity can exceed available host storage: [WSL disk-space guidance](https://learn.microsoft.com/en-us/windows/wsl/disk-space).

## Recovery before experiments

1. Preserve the original stopped Ubuntu disk. A dedicated recovery directory was created on the user's Z: network drive, which has over 6 TB available. No disk migration or repair has run.
2. Obtain approval for the system-wide WSL/Docker interruption needed to release the stale disk handle. Other workloads may use Docker; the experiment's authorization does not presume permission to interrupt them.
3. After shutdown, create and verify a backup before any repair. Inspect the exact Ubuntu device, then choose the least invasive filesystem recovery supported by the observed condition. Microsoft's repair procedure requires an elevated shell and can require closing Docker. Do not guess a block-device name from the historical log.
4. Recover the C8 ledger, manifests, failure records and sampler logs. Retain failed elapsed time and the frozen 90/30-minute cumulative caps; do not reset the experiment budget or remove an active operation without a separately recorded recovery receipt.
5. Establish sufficient actual host headroom before resuming. Task-derived exports and the completed T3 reference cache are candidates for verified archival; original weights and unrelated data are protected. Z: is a network drive, so it is not treated as a drop-in location for a running WSL disk.
6. Freeze the execution repair before comparative outcomes. The new host-storage guard requires an explicit backing-volume path in WSL, checks a 20 GiB reserve plus each proposed output, samples headroom during operations, fails on unreadable storage, and records its observed minimum. Set `C8_HOST_STORAGE_PATH=/mnt/c` only after verifying that C: still backs this distro. Scientific targets, sources, repetitions, formats and nomination rules remain frozen.

The completed T3 curve and source-bound C8 plan are already committed in the companion [evaluation PR](https://github.com/grinder81/polyglot-quant-eval/pull/50). Q3_K_M is the selected operating point under the observed English floor. This interruption supplies no evidence for or against language-informed allocation. The pilot and decision tasks remain unfinished; the holdout remains untouched.

The user's latest allowance instruction supersedes the earlier 10% threshold: stop below 2% weekly allowance. No usage reset was requested or redeemed.

## Recovery record, 6 November 2026

Measured values are in [verification-2026-11-06.json](verification-2026-11-06.json); times are Pacific.

1. **Disk handle and journal.** A Windows power cycle on the morning of 6 November released the stale handle. A read-only inspection command then started the distro at 08:44, before any backup existed; the kernel replayed the ext4 journal and mounted the root read-write. That is the least invasive repair the gate above asked to choose deliberately, and it happened without the backup first. It is recorded here as a deviation; the inspection wrote nothing inside the distro.
2. **Backup.** With the distro stopped, the virtual disk (352,540,688,384 bytes, SHA-256 `ef4714bc…`) was copied to the recovery folder on the network drive between 13:57 and 19:58 (robocopy, exit 1); its size and timestamp were unchanged when the copy finished. The copy was then read back in full from the network drive, from 20:06 on 6 November to 08:47 on 7 November (45,632 s; the network path slowed from about 17 MB/s to 3 MB/s overnight), and its SHA-256 and size equal the fingerprint taken from the source before the copy. The receipt sits beside the copy in the recovery folder and in the verification record. The distro has been started since the copy, so the backup is its state before 19:59 on 6 November.
3. **Health.** The distro was started deliberately at 19:59 for read-only checks: clean read-write mount, no I/O or filesystem errors, GPU visible. The edge test suite passes under the converter environment (15 tests), including the budget tests, which now name the backing volume explicitly, and the recovery tests below.
4. **Artifacts.** 7,226 files (277.7 GB) were hashed against their manifests with no mismatch: the nine completed C8 exports, the five T3 builds and the export-probe build (output hash and size), the BF16 control and the local Q4_K_M control, nine Hub files, the 5,400 per-question comparison records of the six fidelity folders, and the reference cache's 900 per-question records and 900 logit arrays (187.5 GB) against the `cache_sha256` and `cache_bytes` each record carries. The reference manifest hash equals the frozen value in the resume guide; each local fidelity manifest's hash equals the `fidelity_manifest_sha256` committed in the evaluation repository; the local T3 build manifests are identical to the committed copies under `reports/article2-pilot/builds`.
5. **Instrument.** The verified fidelity wrapper re-scored three questions each for Q3_K_M and the local Q4_K_M into a scratch folder outside the workspace. Every non-timing field, including per-token KL, mean KL and top-1 agreement, is identical to the records of 1 November, and the identity block (runtime, implementation and import hashes) is identical.
6. **C8 as found.** Nine passed native rows totalling 414.86 s of the 90-minute cap; one row still active (`export-blk.17.ffn_down.weight-Q3_K`, started 20:00:16.68 on 1 November) and the stale lock naming it; a 197,132,288-byte partial output (last written 20:00:48.06, SHA-256 `73356be3…`); its evidence folder holding only `quantize.log` (51,248 bytes); a zero-length export log; the sampler's last sample at 20:00:47.83. No `failure.json` was written and no comparative probe ran.
7. **Closure, not yet executed.** `builds/recover_c8_interrupted_operation.py` closes exactly one active row as failed with the elapsed time observed from the preserved evidence (start to last observed activity, 31.38 s here), moves the operation's leftovers unchanged into a recovery folder, removes the stale lock with its content recorded, keeps a copy of the ledger as it was, and writes a receipt. It refuses a wrong operation id, a lock that names anything else, an end before the start, any item outside the frozen workspace, and a second receipt. Spent budget is retained; caps, targets, formats, repetitions and nomination rules are unchanged. It runs only after the backup read-back is verified; the remaining seven exports then resume one at a time with `C8_HOST_STORAGE_PATH=/mnt/c`, after the host headroom plan is approved.
